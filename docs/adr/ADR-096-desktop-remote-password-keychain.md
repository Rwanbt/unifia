# ADR-096 — The desktop's remote password lives in the system keychain

**Status:** accepted on `fix/sidecar-credentials-not-inherited`, pending independent review. Corrected after the review of head `2222bfff7`: the statements that review found false are restated below, and *Review of 2222bfff7* lists the changes.
**Date:** 2026-10-12

## Context

The desktop application's remote password is the owner's authority on the server: basic auth is the `admin` role. It was stored in clear in the settings store (`opencode.settings.dat`, under the application data folder), where any process of the same user can read it. ADR-094 recorded this as an open residual.

## Decision

The password is kept in the system keychain, in the install's own entry: namespace `unifia.remote.<flavour>`, key `password`. The flavour comes from the Tauri application identifier (`remote_secret::flavour`): `dev` for `ai.unifia.workbench.dev`, `beta` for `ai.unifia.workbench.beta`, `stable` for `ai.unifia.desktop`, and `custom-<identifier>` for any other. No official flavour starts with `custom-`, so no other identifier can name an official entry: before this, an identifier spelled `dev`, `beta` or `stable` was given the official install's namespace. Two installs of one user therefore never share a password (open decision 6, decided 2026-10-12). The settings store keeps only the username, the enabled flag, TLS, `password_in_keychain` (the keychain holds the password) and `password_in_own_entry` (the password is in this install's entry, not in the shared one). Implemented in `packages/desktop/src-tauri/src/remote_secret.rs` (`Keychain`). `load_remote_config` and `save_remote_config` in `server.rs` pass it the keychain of `app.config().identifier`.

- **Namespace.** The password is read and written through the raw keychain backend, on the install's own namespace only (`unifia.remote.<flavour>`). The shared namespace `unifia.remote` is what every install wrote before the entries were per install. It is read by one adoption (see *Adoption*), and it is never written or deleted. The shim's helpers fall back to `opencode.remote` when the new entry is empty, and another product may write that entry. The remote password never adopts a value from it.
- **Migration.** A settings file that still holds a password in clear reads the install's own entry first. If the keychain is empty, the password is written there and read back, and the settings file is rewritten without it only after the read-back matches (`Migrated`). If the keychain already holds a different password, the keychain's stays active, the settings file's copy is dropped, the desktop logs a warning, and the settings file is rewritten (`Superseded`). If the keychain cannot be read, or cannot be written and read back, nothing is written to it, by a load or by a save, and the settings file keeps the password it held in clear (`LegacyKept`). A save in that state writes the settings file with that password unchanged, and the flag at `false`. A configuration without a remote section has a random default password, which is never written to the settings file. Both cases are logged.
- **Adoption (decided 2026-10-12).** A settings file that flags the password as stored, without `password_in_own_entry`, was written before the entries were per install, so its password is in the shared entry. That install copies the shared password to its own entry, reads it back, and sets `password_in_own_entry`. The result is `Adopted`, and the settings file is rewritten. The shared entry is left unchanged and never deleted. The flag makes this happen once per install: an install that holds its own entry never reads the shared one again. A password it then no longer finds is `Lost`, and a new one is generated, never the shared entry's, which another install may have reset since. A shared entry that is empty gives `Lost` as well. If the copy cannot be written and read back, the shared password is kept for the run only, the flag stays unset, and the next launch adopts again. An install with no flag and no entry generates its own password, and never reads the shared entry. Without a readable settings file, only the install's own entry is read. The adoption is once per install, not once for the user: two installs that both carry the flag each copy the shared password on their first launch, so they start with the same password and differ from their next reset on.
- **Lost entry.** A flagged password that the keychain no longer holds is replaced by a new one, and that new one is kept (`Lost`). Clients paired with the old password must pair again. The desktop logs a warning that says so. This is the recovery path, and it is logged. That includes a password generated when the settings store cannot be opened and the keychain holds none: before the review it was silent there, and it is now logged as lost.
- **Keychain unusable.** On the first load of a run, a keychain that cannot be read gives a password for this run only (`Unavailable`). That password is session-only: no save writes it to the keychain, and nothing from it reaches the settings file. Later loads of the run return the same password (see *Run password*). A save in that state keeps the settings flag at `true`, because the keychain entry is still the one recorded. The next launch therefore reads the stored password again when the keychain works. If the keychain holds nothing, the password is reported as lost. A keychain that cannot take a new password gives the same session-only password.
- **Owner's choice.** `set_remote_credentials` with a non-blank password, and `reset_remote_password`, clear the session-only mark (`remote_secret::replace`). The password the owner chose is then written even when the stored one could not be read. Once the keychain has accepted it, the run adopts it (`RUN_PASSWORD.adopt`), so the UI shows it.
- **Rotation.** `reset_remote_password` overwrites the keychain entry. The application keeps no copy of the old value. The running sidecar keeps the password it was started with until it restarts (see Open decisions). **After a reset the UI shows the new password while the sidecar still checks the old one.** The settings screen says the change takes effect after restart (`settings.desktop.remote.password.description`). Until then, a client given the new password is refused.
- **Run password.** A process holds one password for its run (`RUN_PASSWORD`). The first load resolves it against the keychain, and every later load returns it, whatever the keychain holds then. The sidecar is started with the first one, so the password the UI shows is the one the sidecar checks, until the owner sets or resets a password. A later load reads the keychain only to decide what a save may write: a keychain that holds another password is not overwritten, and the run keeps its own (`Diverged`, logged); a password drawn for the session is never written; a keychain that holds nothing gets the run's password back, unless the run's password is a session password.
- **Keychain commands.** `auth_storage_get`, `_set`, `_delete` and `_list` name only the entries their callers use: the sidecar's provider credentials (service `auth`, any provider key) and the GitHub session (`github` / `session`). Every other entry is refused, including `remote/password`, the per-install `remote.<flavour>` entries, and their case variants. Each command delegates to an operation (`get_entry`, `set_entry`, `delete_entry`, `list_entries`) that runs the check first, so the sidecar's `/kc/` route, which calls the same operations, is held to it too.
- **What the webview can reach.** The allow-list keeps `remote/password` out of the keychain commands. It is not a limit on the webview as a whole. The main window's capability is `windows: ["*"]`, and `build.rs` declares no app manifest, so the app's commands carry no per-command permission and are callable from the webview. The webview can therefore call `auth_storage_get`, `_set`, `_delete` and `_list` for the provider entries (service `auth`) and the GitHub session (`github` / `session`). The application's own frontend does not call them (a search of `packages/app/src` and `packages/desktop/src` finds no call). The webview also holds the owner's password, by design: `await_initialization` returns the sidecar's username and password (`ServerReadyData`), and `get_remote_config` returns the remote password, the port and the TLS fingerprint, which the pairing QR code is made from. A script that runs in the webview can therefore read the owner's password. That is the price of pairing from the desktop, and it is not changed here. Not run: a webview calling the commands (see *Not verified*).
- The sidecar does not read the settings store for the password. The desktop hands it over on the credential line (ADR-094).

## Verified here

- `cargo test --lib` of `unifia-desktop` on Linux: 122 pass, 0 fail, on the head that carries these corrections (111 on `2222bfff7`). Of these, 28 are in `remote_secret` and 9 are in `auth_storage`. The additions after the review of `2222bfff7` cover the legacy password and the random default under a failed keychain read, the lost entry without settings, the password of a run across loads, a keychain that another install changed, a session password that is never written, and the keychain commands refusing the remote entry through their operations. The `remote_secret` tests use a mock keychain, a keychain that fails every call, and a keychain whose reads fail while its writes are kept. They cover the migration cases above, the lost entry (resolved to `Lost`, with its warning), the first launch, a save after a failed read that leaves the stored password in place, an owner's password written after a failed read, the legacy namespace not being adopted, and a refused write returned as an error.
- The `auth_storage` tests: the remote entry is refused by get, set, delete and list, including its case variants. The sidecar's and GitHub's entries are accepted.
- Mutation check on this head: putting the password back into the settings form fails `the_settings_form_after_a_migration_holds_no_password`, `the_settings_bytes_after_a_migration_hold_no_password_value` and `a_save_after_a_failed_read_leaves_the_stored_password_in_the_keychain`. The change was reverted, and the tree matched the commit.
- Per-install entry (2026-10-12): `cargo test --lib` of `unifia-desktop` on Linux: 133 pass, 0 fail (122 before, plus 11 new). The `remote_secret` tests use a mock keychain. Two installs have separate passwords, and a reset in one does not change the other. Before this change, after the development install reset its password, the stable install's next launch checked the reset password instead of its own, and the test failed on that code. A new install with no flag generates its own entry and never reads the shared one, shown with a keychain that records its reads. A flagged install adopts the shared password once, leaves the shared entry unchanged, and does not adopt it again after the shared entry is reset and the install's own entry is lost. An unreadable copy keeps the shared password for the run only. A change in another install's entry does not make a run diverge. The Diverged guard still applies to the install's own entry (`a_keychain_holding_another_password_is_not_overwritten_by_a_save_of_the_run`). The `auth_storage` test refuses the per-install entries.
- `cargo check` of `unifia-desktop`: exit 0, zero warnings. `rustfmt --edition 2024 --check` is clean on the changed Rust files.
- Not run: the keychain of Windows (Credential Manager) and macOS, with the per-install names, the Secret Service on Linux with a live session, an installed application upgrading from the shared entry, a Windows build, and a running webview calling the keychain commands.

## Not verified here, and residual risk

1. **Old copies of the plaintext.** The settings store is rewritten without the password, but a copy of the previous file may remain in free blocks, a file-system journal, a backup, or a synchronised folder. The application cannot erase those. This is stated, not claimed as removed.
2. **Keychain unavailable on a legacy install.** The password stays in the settings file, with a warning in the log. The plaintext residual therefore remains on that machine until the keychain works.
3. **Keychain unusable at launch.** The password is for that run only, so a client paired with it stops working at the next launch. The operator sees a warning. This favours a visible failure over a stored secret.
4. **A same-account process.** The keychain entry is readable by the same account where the operating system's policy allows it. The keychain is a better boundary than a settings file, not a barrier against a same-account process, which can read the desktop's memory or ask the keychain itself.
5. **Backup and recovery.** The application does not export the password. A lost keychain entry is recovered by generating a new one, which invalidates the paired clients. A controlled backup of the password is not implemented, and is a decision for the owner.
6. **The username** stays in the settings store. It is not secret.

## Open decisions and known defects (not changed here)

1. **Rotation takes effect on restart (owner's decision).** `reset_remote_password` overwrites the keychain entry and returns the new password to the UI. The sidecar was started with the old one (`load_remote_config` at startup, in `lib.rs`, then `cli::serve`, which hands it to `cli::spawn_command`), and it checks basic auth against that value until it exits. Until the next launch, the old password stays valid and the new one is refused. The UI says the change takes effect after restart. Two options:
   - (a) Keep the restart requirement. The old credential remains valid after a rotation, which is the reason for rotating.
   - (b) Restart the sidecar inside the reset. The old credential stops at once, but every open PTY WebSocket and SSE stream is dropped. `set_remote_enabled` gives that as its reason for not restarting at runtime. The desktop's own connection must also take the new password from `ServerReadyData`, which is fixed at startup.
2. **Fixed after review.** The session-only password is drawn once per process (`session_password`). Before, each load drew a new one, so one run could return a password different from the one the sidecar was started with.
3. **Fixed after review.** A settings store that cannot be opened no longer yields a random, unsaved password. `resolve_without_settings` lets the keychain decide: a password it holds is used, and a new one is generated only when it holds none. A warning is logged that the settings are neither read nor saved.
4. **Fixed after review.** A new password is never written over a stored one. `generate` reads the keychain first, keeps a password it already holds, and writes nothing while the keychain cannot be read. Before, a settings file with no password and no flag replaced whatever the keychain held, silently. This holds for generation. A legacy or default password, while the keychain's state is unknown, was still written over it on a save until the review of `2222bfff7` (see *Review of 2222bfff7*).
5. **A lost entry whose regeneration cannot be written** is reported as session-only (`Unavailable`), not as lost.
6. **One keychain entry per install (decided 2026-10-12).** Each install keeps its password in `unifia.remote.<flavour>`, where the flavour comes from the application identifier (`dev`, `beta`, `stable`, or `custom-<identifier>` for any other). A reset in one install no longer changes another install's password. The consequences the owner accepted: the settings file gains `password_in_own_entry`, which is a flag and not a secret. A settings file copied to another install names an entry that install does not hold, so that install reports `Lost` and generates its own password. The first launch after the change adopts the shared entry once for each install that carries the flag (see *Adoption*). Not checked: the Windows and macOS keychains with the new names, and an installed application that upgrades from the shared entry.

## Consequences

- The settings store no longer holds the owner's password, after the first load on a machine whose keychain works.
- A desktop whose keychain cannot be read runs with a password for that run only. A client paired with it stops working at the next launch.
- ADR-094's open item on the plaintext password is closed by this decision, subject to review and to the Windows and macOS keychains being checked.
- Each install has its own keychain entry (open decision 6, decided 2026-10-12). The shared entry is adopted once per install that carries the flag, and it is left as it is.

## Review of 2222bfff7

An independent review of `2222bfff7` found the defects below. Each is fixed by its own commit on this branch. The regression tests for the first three failed on `2222bfff7`; the keychain-command gap was shown by a mutation that the existing tests did not catch.

- **Legacy and default password under a failed read (`LegacyKept`).** A save wrote the in-memory password over the keychain value it had not read. `LegacyKept` now writes nothing to the keychain. The settings form keeps the password the file held in clear, and no other. A configuration without a remote section keeps its random default out of the settings file.
- **Lost entry without settings.** A password generated when the settings store cannot be opened, over an empty keychain, was mapped to `Generated`, which has no warning. It is `Lost`, and logged.
- **The password of a run.** Each load resolved the keychain again, so the UI could show a password the sidecar did not check. `RUN_PASSWORD` fixes the password at the first load, and every later load returns it. A later load reads the keychain only to decide what a save may write (`Diverged`, a session password, an empty keychain). The owner's reset or set is adopted once the keychain has accepted it.
- **The keychain commands.** The check is in the operations the commands call, and the tests run those operations. Removing the check from `auth_storage_get` passed every test on `2222bfff7`; it now fails two.
- **Not changed, for the owner's decision.** The voice helper (see ADR-094), and open decision 6 (one entry for every install). The webview's reach is stated under *Keychain commands*.

A save still re-reads nothing: the load that precedes it reads the keychain, and a change to the entry between that read and the save is not seen. The window is the length of one command. It is not closed here.
